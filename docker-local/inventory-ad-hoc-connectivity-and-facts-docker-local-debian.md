# Inventory, Ad-hoc Connectivity and Facts (docker-local, debian)

## Overview

This exercise builds the connection layer that every later exercise stands on. One Debian 12 container, `inventory-adhoc-facts-debian-node1`, runs on the local Docker daemon with an `ansible` user and a key-based SSH login. The exercise directory holds three files, `inventory.ini`, `ansible.cfg` and `site.yml`. Together they let the controller (the devcontainer) reach that node by a stable name, prove that a module can run there, read what the node reports about itself, and assert that those reports are what we expect. Nothing on the managed node is changed at any point. The whole exercise is read-only, and that shapes what the idempotency check can and cannot prove.

The intuition is simple. A manual login like `ssh -i .tmp/ansible_node_key ansible@172.17.0.3` carries an address, a user and a key in one command line, and Ansible needs exactly those facts for every host it manages. The inventory is where those facts are written down once per host, so that no command has to repeat them.

## Inventory host lines and connection variables

An INI inventory is read line by line. A `[debian]` header opens a group, and every following line until the next header declares one host in that group. The first whitespace-separated token on a host line is the host's name, and each later token of the form `key=value` becomes a variable attached to that host. Two consequences of this rule caused real defects during the session. Writing one variable per line produced three hosts whose names were literally `address=127.0.0.3`, `user=ansible` and `key=...`. Separating variables with commas made each comma part of the preceding value, so the user variable became the string `ansible,`. The name `node1` is a label, not an address. It stays stable when the container's IP changes, and only the `ansible_host` value has to be edited.

Ansible stores any `key=value` it finds, but the SSH connection plugin reads only a fixed set of reserved names. `ansible-doc -t connection ansible.builtin.ssh` lists, for each option, a `vars:` section giving the inventory variable names that set it: `ansible_host` for the address, `ansible_user` or `ansible_ssh_user` for the login user, and `ansible_private_key_file` or `ansible_ssh_private_key_file` for the key. The same entry also has an `ini:` section, which names the key for `ansible.cfg` (for the key file, `private_key_file` under `[defaults]`). Using an `ini:` name as an inventory variable is silently useless. The variable exists, but the connection plugin never consults it. A static inventory declares hosts and does not discover them. If Docker hands the node a new IP tomorrow, the file is wrong until someone edits it, which is the problem dynamic inventory plugins exist to solve.

## How ansible.cfg is found

Ansible looks for its configuration in a fixed order and stops at the first match: the `ANSIBLE_CONFIG` environment variable, then `./ansible.cfg` in the current working directory, then `~/.ansible.cfg`, then `/etc/ansible/ansible.cfg`. In this devcontainer none of the last three exist and the variable is unset, so `ansible --version` reports `config file = None` from anywhere except the exercise directory. The exercise's `ansible.cfg` contains a single setting, `inventory = inventory.ini` under `[defaults]`. Its `ansible-config list` entry carries `expand_relative_paths: true`, so the relative path resolves against the config file's own directory.

## Observable behavior

`ansible-inventory --graph --vars` shows `node1` under `@debian` under `@all` with its four variables, and it touches no network to do so. Ad-hoc `ansible debian -m ansible.builtin.ping` returns `SUCCESS` with `"ping": "pong"` and `"changed": false`. With a mistyped key path it returned `UNREACHABLE`, because the SSH client had no identity to offer and the node answered `Permission denied (publickey,password)`. Before the interpreter was pinned, the successful ping also printed an interpreter-discovery warning and an `ansible_facts.discovered_interpreter_python` entry; after pinning, both disappeared. `setup -a 'filter=ansible_distribution*'` reports `Debian`, major version `"12"` as a quoted string, release `bookworm`, and the source file `/etc/os-release`. The playbook's recap is `ok=4 changed=0 failed=0` on the first run, on the second run and under `--check`. Running the ad-hoc ping from the repo root with no inventory printed three warnings and exited with code 0.

## Internal mechanism

When `ansible-playbook site.yml` starts in the exercise directory, it finds `./ansible.cfg`, reads the inventory path from it, and parses `inventory.ini`. The play's `hosts: debian` is a pattern matched against that inventory, so only members of `debian` run it. For `node1`, the connection plugin builds an SSH login from `ansible_host`, `ansible_user` and `ansible_private_key_file`, with port 22 as the default. The implicit Gathering Facts task is the `setup` module. It is copied to a temporary directory on the node and executed by `/usr/bin/python3.11`, which is named directly by `ansible_python_interpreter`, so no discovery probe runs. It reads the node's own `/etc/os-release` and prints its result as JSON, which SSH carries back to the controller. The controller stores these facts in `ansible_facts` with the `ansible_` prefix removed, so the key is `ansible_facts['distribution']`. Because `inject_facts_as_vars` defaults to true, it also exposes a prefixed top-level copy, `ansible_distribution`. Each `assert` then evaluates its `that:` expressions as Jinja2. The version fact is a string, so it is converted with `| int`. The filter binds tighter than `==`, giving `(fact | int) == 12`. No facts survive between runs, because no fact cache is configured.

## Design rationale

Connection details live in the inventory because they differ per host. The config holds only what is common to the whole exercise, and keeping it per-exercise means every behavior comes from a file visible in this directory, with nothing inherited from a shared config. Connectivity is proved with the `ping` module because it exercises the full chain: login, module transfer, remote execution with Python, and JSON back. An ICMP ping proves only the network path, and `ssh ... true` proves only the login. The interpreter is pinned to `/usr/bin/python3.11` rather than silenced with `auto_silent` or pointed at the `/usr/bin/python3` symlink. On a distro upgrade that removes 3.11, the run fails loudly instead of silently moving to an interpreter that may lack distro-packaged libraries such as `python3-apt`. Silencing would hide that risk, not remove it. Verification uses `assert` against facts, and one assert was deliberately broken to show that it can fail, because an assert that has only ever passed is not evidence of anything. Since every task only reads, the first run's `changed=0` already shows the playbook modifies nothing, and the second run is a formality here.

## Edge cases

The devcontainer reaches Docker as a sibling (Docker-outside-of-Docker), so published ports land on the host, not on the devcontainer's `127.0.0.1`. The node is therefore reached on its bridge IP, `172.17.0.3`, port 22, and the key's bind mount must use the host-side path of the workspace. A host pattern that matches nothing, for example when run from a directory with no config, prints warnings and exits 0, so an exit-code check alone would report success when nothing ran. The asserts check properties, not identity: a different Debian 12 machine with an `ansible` user would pass them all. Finally, the connection currently relies on the node's host key already being in the controller's `~/.ssh/known_hosts`. A recreated container on a reused IP would present a new key and fail host-key verification, and how to handle that is left for a later exercise.

## Worked example

Take the deliberately broken run, where the version assert reads `ansible_facts['distribution_major_version'] | int == 13`. The play matches `node1` through the `debian` group, and Gathering Facts logs in as `ansible` at `172.17.0.3:22`, runs `setup` under Python 3.11 and brings back `distribution` as `"Debian"` and `distribution_major_version` as `"12"`. That task reports ok, so the count is one. The first assert compares `"Debian"` with `"Debian"`, which is true, so it reports ok and the count becomes two. The second assert converts `"12"` to the integer 12 and compares it with 13, which is false, so the task fails for `node1`.

A failure removes the host from the rest of the play, so the third assert never considers `node1` at all. It is not counted as skipped, because skipped means a task looked at the host and a `when:` condition declined it. The recap therefore reads `ok=2 changed=0 failed=1 skipped=0`. After reverting the value to 12, the same trace yields four ok tasks and `changed=0`, and that result repeated on an immediate second run.
