# Host Key Checking for Recreated Containers (docker-local)

## Overview

This exercise deals with the "Host key verification failed" error that blocked the first connection in both earlier exercises. It uses two docker-local nodes: `inventory-hostkeys-node1` from the Debian 12 image and `inventory-hostkeys-node2` from the Rocky 9 image. Two families are used only because their host keys differ, not as a module comparison. The session corrects the premise that a recreated container presents a new host key, then compares what each available fix gives up, and finishes with a strict policy: SSH must refuse both an unknown key and a changed key, and the correct key is placed in a per-exercise file, before the first connection, through a channel that does not involve SSH. This is the first exercise in the repo with tasks that report `changed`. Those tasks change files on the controller, not on the nodes.

## Host keys and the two failure cases

An SSH server presents its host key as its identity, and the client compares it with the entry its known-hosts file holds for the dialled address. Whoever accepts an unknown key first decides which key counts as genuine, a pattern called trust on first use. Two cases fail this comparison. In case A the key is unknown, because no entry exists for the address. In case B the key has changed, because an entry exists for the address but holds a different key. When Ansible adds nothing to the command line, OpenSSH uses its own default, `StrictHostKeyChecking=ask`. In case A, `ask` tries to prompt the user through `ssh-askpass`; with no terminal and no askpass helper the prompt cannot happen, and the connection is refused. In case B, `ask` refuses at once with `REMOTE HOST IDENTIFICATION HAS CHANGED!` and never prompts. Without a terminal, then, `ask` refuses in both cases, exactly as `yes` would.

Both node images create their keys at build time. On Debian the post-install script of `openssh-server` generates them during `apt-get install`, and on Rocky the Dockerfile runs `ssh-keygen -A`. Every container started from one image therefore presents the same key, and the `.pub` comment `root@buildkitsandbox` names the build sandbox where that key was made. The failures in the earlier sessions were case A: the README's teardown step runs `ssh-keygen -R <ip>`, which deletes the entry, so the next container's key was unknown. Case B on this setup happens when a Debian node and a Rocky node swap bridge IPs, and this session produced it on purpose by recreating the containers in the opposite order.

## Observable behavior

Run against an empty known-hosts file, the baseline ad-hoc ping reported UNREACHABLE on both hosts, with `ssh_askpass: exec(/usr/bin/ssh-askpass): No such file or directory` followed by `Host key verification failed`. With `host_key_checking = False`, case A connected and was recorded in `~/.ssh/known_hosts`, and case B connected silently, with the warning visible only at `-vvv`. For `site.yml`, `--check --diff` reported the exec task `ok` and the `known_hosts` task `changed`, with each host's diff starting from `/dev/null`, and the file was not created. The first real run reported `changed=1` per host and left the file with two lines, each pairing an IP with that container's ECDSA key. Later runs reported `ok=4 changed=0`. In the negative test, where the IPs were swapped and the inventory left stale, the seeding tasks reported `ok` and `setup` went UNREACHABLE with `Host key for 172.17.0.4 has changed and you have requested strict checking`.

## Internal mechanism

The plugin's `ini:` and `vars:` option sources are covered in `inventory-basics.md`. Setting `host_key_checking = False` makes Ansible add `-o StrictHostKeyChecking=no` to the command line and nothing else. `True` adds nothing at all, which leaves OpenSSH's default in force. `ssh_common_args` is read only from the `[ssh_connection]` section of `ansible.cfg`. When placed in `[defaults]` it was ignored without any warning, and `ansible-config dump --only-changed` does not list connection-plugin options, so the dump cannot reveal the mistake. Once the option is read, its text is pasted unchanged onto every `ssh`, `scp` and `sftp` command line, so `-o UserKnownHostsFile=<path>` makes OpenSSH consult that file instead of `~/.ssh/known_hosts`. A relative path would resolve against Ansible's working directory.

The play targets `all` with `gather_facts: false`, because fact gathering is itself a task that runs on each node and would go UNREACHABLE before trust exists. The first task, `community.docker.docker_container_exec`, runs `cat /etc/ssh/ssh_host_ecdsa_key.pub` in the container named by the `container_name` host variable. The `delegate_to: localhost` keyword makes the task run on the controller while host variables such as `ansible_host` still refer to the current node. The `register: host_key_result` keyword stores the module's return value for that host. The module always reports `changed`, so `changed_when: false` overrides the report, and this is honest because `cat` only reads. Because the module cannot predict its effect, Ansible skips it under `--check`, registering a skip record with no `stdout`; `check_mode: false` makes it run for real even in a dry run, which is safe for the same reason. Next, `ansible.builtin.known_hosts`, also delegated, compares the line `"{{ ansible_host }} {{ host_key_result.stdout }}"` against the file at `path`. Its `name` must equal the first field of that line. The module writes only when the line differs, replacing an existing entry of the same host and key type. After seeding, an explicit `ansible.builtin.setup` task is the only task that opens SSH to the node. The final `assert` is an action plugin that runs on the controller and compares the gathered `ansible_facts['distribution']` with the per-group `distribution` variable.

## Design rationale

`host_key_checking = False` was rejected because in case B it lets an impostor at a reused IP connect, and at default verbosity nothing tells you. `accept-new` was rejected too, because it is still trust on first use. The key source is the Docker daemon rather than `ssh-keyscan`. `ssh-keyscan` trusts whatever answers at an address, while the daemon resolves a container name to the container it created, so feeding it a false key requires compromising the daemon or the host. Running `cat` through `docker_container_exec` is an arbitrary command, but no dedicated module reads a file out of a container without SSH (`docker_container_copy_into` only copies in), so it is the narrowest tool. The known-hosts file belongs to the exercise for two reasons. A shared file mixes entries from different exercises and sittings, which is how `~/.ssh/known_hosts` ended up holding wrong keys for .3 and .4. A file owned by the exercise also follows the repo rule that an exercise inherits nothing silently from outside its own directory. Committing the file is acceptable because host keys are public. Entries that go stale next sitting fail safe, since strict checking refuses them, and the seeding task rewrites them on its next run. The path is absolute, like the private-key path. One play with an explicit `setup` task makes the order visible: trust is written before the one task that needs it.

## Edge cases

The seeding binds a key to the container's identity, but it files that key under whatever IP the inventory claims. A wrong address in the inventory therefore surfaces as UNREACHABLE, never as a silent connection to the wrong machine. Both hosts' delegated `known_hosts` tasks write one controller file in parallel; every run produced two correct lines, but whether concurrent writes can lose an entry was not investigated. Only ECDSA keys are seeded.

## Worked example

Take the negative test. The file holds `172.17.0.4 <Debian ECDSA key>` and `172.17.0.3 <Rocky ECDSA key>`. The containers are recreated with node1 (Debian) started first, so Docker gives it .3 and Rocky gets .4, while `inventory.ini` still says `node1 ansible_host=172.17.0.4`. For node1, the exec task asks the daemon for `inventory-hostkeys-node1`, the real Debian container, so `host_key_result.stdout` is the Debian key and the task reports `ok`. The `known_hosts` task builds `172.17.0.4 <Debian key>`, finds exactly that line already present, and reports `ok` without writing. The `setup` task then opens SSH to .4, where the Rocky container answers with the Rocky key. OpenSSH reads the exercise's file through `UserKnownHostsFile`, finds an entry for .4 that holds a different key, and refuses under the default `ask`, so node1 ends as `ok=2 unreachable=1` and the assert never runs. Correcting the inventory to node1 = .3 makes the next run write `172.17.0.3 <Debian key>` over the old Rocky line, which is a replacement, so the file still has two lines. That run reports `changed=1`, `setup` succeeds, the assert sees `Debian == Debian`, and the run after it reports `ok=4 changed=0`.
