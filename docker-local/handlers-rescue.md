# Block and Rescue Revert of a Failed Config Change (docker-local, debian+rhel)

## Overview

`handlers-notify.md` ended with a node left in a split state. A drop-in that `validate` accepted on its own was moved into `/etc/ssh/sshd_config.d/`, the merged `sshd -t` check then rejected it, and the host failed. The bad file stayed on disk while the running sshd kept the old configuration in memory. If the container later restarted for any unrelated reason, sshd (PID 1) would refuse the merged configuration and exit, the container would stop, and Ansible would have nothing to connect to. This exercise makes the play undo its own change when the check fails. It reruns the handlers-notify play on two fresh docker-local nodes, `handlers-rescue-node1` (Debian 12, OpenSSH 9.2p1) and `handlers-rescue-node2` (Rocky 9, OpenSSH 9.9p1), with Render and the merged check wrapped in a block. The block's rescue section puts back exactly what was there before. Inventory, host-key seeding, the restart handler and the `wait_for` banner check are reused unchanged from `handlers-notify.md`, `inventory-dynamic.md` and `inventory-hostkeys.md`. These notes run past the usual 1400-word ceiling on purpose, because the session is a synthesis. It combines block and rescue error handling, the template module's backup mechanism, `when` with Jinja2 tests, and a revision of where the handler notification sits, and each of these needed its own trace.

## Blocks, rescue and conditions in plain terms

A block is a single item in a task list that groups several tasks under a `block:` key. It can carry a `rescue:` list and an `always:` list as sibling keys on the same item. When any task inside `block` fails on a host, the remaining block tasks are skipped for that host and the `rescue` tasks run instead. If rescue completes, the host is no longer considered failed: the recap counts it under `rescued=1`, and the host carries on with the rest of the play. The `always` list runs either way. It was discussed in this session but not used in the final play. Inside rescue, Ansible supplies `ansible_failed_task` and `ansible_failed_result`, which hold the failed task and its full result, much like a `register` nobody wrote. The Ansible docs warn that unreachable hosts and invalid task definitions do not trigger rescue.

Three ideas this session introduced are used throughout. The `when:` keyword holds a bare expression, without `{{ }}`, and the task runs only if it is true; otherwise it reports `skipped`. A Jinja2 test, written `<value> is <test>`, answers a yes/no question. Here the tests are `is changed`, `is defined` and `is not defined`. `register` stores a task's result even when that task fails.

## Observable behavior

On fresh nodes with the good one-line template, the final play reported `ok=6 changed=3` on both hosts on the first run. The three changes were Render, Verify and the restart handler, and the immediate second run reported `ok=5 changed=0`. With the template given the extra line `Subsystem sftp /usr/lib/openssh/sftp-server`, the hosts diverged. The two failing cases ended the same way in the recap, `failed=1 rescued=1` with no restart, but they differed in the task lines and on disk. In case A, a fresh node1 with no previous drop-in, Render reported `changed`, Verify `failed`, Remove SSH Banner `changed`, Revert SSH Banner `skipped`, and Explain SSH Banner Failure `failed`; the recap read `ok=4 changed=2 failed=1 skipped=1 rescued=1`, and `sshd_config.d/` ended empty. In case B, a converged node1 with a good drop-in, Revert ran instead of Remove, so the good 38-byte file was restored and one `10_banner.conf.<pid>.<timestamp>~` backup remained beside it. Node2 accepted the same line; on a fresh node2 that run created the drop-in, restarted it and reported `ok=6 changed=3`, while on later runs, where node2 already carried that drop-in, it reported `ok=5 changed=0` with no restart. Node1 then took no further part in the play: the flush and `Ensure Banner is Applied` ran for node2 only.

A template line that sshd rejects on its own made Render fail at `validate` on both hosts. Both rescue tasks were skipped, the fail task fired, and both recaps read `ok=2 changed=0 failed=1 skipped=2 rescued=1`. Neither the flush nor `Ensure Banner is Applied` printed at all. `10_banner.conf` was untouched on both nodes, yet each gained a new `~` backup stamped with that run's time. The `TASK [Run pending handlers]` header printed once whenever only one host was still active at the flush, and twice when both were.

## Internal mechanism

Render carries `backup: true` and `register: ssh_banner_result`. A localhost demonstration showed what the backup parameter does on three successive runs. The first run created the file and reported `changed`, but returned no `backup_file` key, because there was nothing to copy. The second run changed the content, saved the old file as `<dest>.<pid>.<YYYY-MM-DD@HH:MM:SS>~`, and returned that path as `backup_file`. The third run reported `ok` and returned no backup. `ansible-doc ansible.builtin.template` lists no `backup_file` return value. `ansible.builtin.copy` documents it as "returned: changed and if backup=yes". That condition leaves out "and the destination already existed".

The rescue undo depends on why there is no backup. In case A Render changed and nothing existed before, so undoing means deleting the file: `ansible.builtin.file` with `state: absent`, guarded by `ssh_banner_result is changed and ssh_banner_result.backup_file is not defined`. In case B Render changed and replaced a file, so undoing means copying the backup back: `ansible.builtin.copy` with `src: "{{ ssh_banner_result.backup_file }}"`, `remote_src: true` (the source is on the managed node, not the controller), and the same `mode`, `owner` and `group` as Render. The guard is the same with `is defined`. The `is changed` half matters because of the `validate` failure. There Render fails without writing anything, and `backup_file` is undefined there too, so a guard on `backup_file` alone would delete a good file.

Verify stays an `ansible.builtin.command` task for the reason given in `handlers-notify.md`: no module validates sshd's merged configuration, and `validate` sees only the drop-in on its own. The notification moved from Render to Verify, which now carries `changed_when: ssh_banner_result is changed` and `notify: Restart Container`. Ansible sends a notification only when the task's result is changed and not failed. Verify is therefore changed only when Render changed something, and it can notify only when `sshd -t` also passed. On the failing run Verify's result showed `"changed": true` and still queued nothing. The last rescue task, `ansible.builtin.fail` with `msg: "{{ ansible_failed_result.stderr }}"`, fails the host after the undo. A failed host is removed from the rest of the play, as `inventory-basics.md` established, which is why the flush and `Ensure Banner is Applied` never run for it.

## Design rationale

Render and Verify share one block because they form a single unit: make the change, then prove the whole configuration still holds. Rescue undoes Render's change, and it has to handle both ways the unit can fail, including the `validate` failure where there is nothing to undo.

The notification placement was revised after an observed failure. With `notify` on Render, case B reported Render `changed`, Verify `failed` and Revert `changed`, yet the recap read `ok=6 changed=3 failed=0 skipped=1 rescued=1` and `RUNNING HANDLER [Restart Container]` restarted node1. A completed rescue clears the host's failure, so the notification Render queued earlier is never dropped. The restart reloaded the same good configuration and achieved nothing except dropping every open SSH connection. Gating the notification on Verify ties the restart to "changed and verified". The cost is a less literal recap: Verify is a read-only `sshd -t`, yet it reports `changed` on every good change, so the good-change recap reads `changed=3` where the actual modifications were Render and the restart. That is accepted in exchange for a handler that cannot fire on a rolled-back change. Using `changed_when` rather than `when` matters separately, because `changed_when` still runs `sshd -t` on every run, whereas `when` would skip the check in the steady state.

Rethrowing after the undo was chosen over letting rescue swallow the failure. Without it, the recap read `ok=5 changed=2 failed=0 skipped=1 rescued=1` and the exit code was success, even though the requested change had been rolled back. Under CI that would show green for an undelivered change. The analogy is a catch block that cleans up and then rethrows. A failed host no longer gets `Ensure Banner is Applied`, and that costs little, because the reverted configuration is the old one.

The `fail` message reads `stderr` so the operator sees `Subsystem 'sftp' already defined`, not only `rc=255`. The failed template result in the `validate` case also carried `stderr`. A failing task without that key would make the message itself fail to render; this was reasoned, not observed.

## Edge cases

Backups accumulate without limit. Every changing run leaves a `~` file, and node1 reached six of them across the session. The `Include` glob is `*.conf`, so sshd ignores them. The `validate` failure leaves an orphan: a backup the play cannot name, because the failed result has no `backup_file` key. This shows the module saves the destination before validating the new content. The backup name contains a node-side PID and timestamp, so a cleanup would have to match `10_banner.conf.*~` with `ansible.builtin.find` and delete each match with `ansible.builtin.file`. That needs a loop, so the cleanup was deferred. A `shell: rm -f` glob was rejected because a proper module exists for the job, and because `rm -f` would report `changed` on every run or hide real deletions behind `changed_when: false`.

The failure path never converges. Each run re-renders the reverted file, fails, and reverts again, and node1 reported `changed=2` on four successive runs with the Subsystem template. That is the correct outcome for a state that cannot be reached, which is why the idempotency check applies to a template that can converge. `sshd -t` checks the configuration's internal consistency, not whether referenced files exist. With the Debian sftp path, node2 passed and became green but broken: Ansible logged "sftp transfer mechanism failed" and "scp transfer mechanism failed" for 172.17.0.4 until a run with the good template restarted node2, after which the warnings disappeared. No functional SFTP check exists.

The doubled flush header has a simple cause. A localhost probe with three hosts printed `TASK [Flush]` three times, and with one host once: a `meta` task is announced once per active host, not once per batch.

## Worked example

Take two freshly recreated nodes, neither of which has `10_banner.conf`, and run the final play with the Subsystem line added to `banner.j2`. Collect and Write report `ok` on both, because the host keys come from the image and the known_hosts file already holds them. On node1, Render finds no destination, and the rendered file passes `validate` on its own. The module creates the file and reports `changed`, and since there was nothing to copy, `backup_file` is absent from `ssh_banner_result`. Verify runs `sshd -t` on the merged configuration. The drop-in, included first, defines `Subsystem sftp`, and line 115 of Debian's own `sshd_config` defines it again, so OpenSSH 9.2p1 exits with status 255. The command fails, and although `changed_when` evaluates true, a failed result queues no notification.

Rescue starts for node1. Remove's guard, `is changed and backup_file is not defined`, is true, so it deletes the file and reports `changed`. Revert's guard is false, so it is skipped. Explain SSH Banner Failure fails with the `stderr` text, and node1 leaves the play with an empty `sshd_config.d/`, which is exactly its fresh state. Its recap was `ok=4 changed=2 failed=1 skipped=1 rescued=1`, with the two changes being Render and Remove.

On node2, Render also creates the file, and OpenSSH 9.9p1 accepts the merged configuration. Verify therefore reports `changed` and queues the restart. The flush runs for node2 alone, so its header printed once. `RUNNING HANDLER [Restart Container]` listed only node2, `wait_for` found the banner, and node2's recap was `ok=6 changed=3`. Its directory afterwards held `10_banner.conf` and `50-redhat.conf` and no backup, a configuration that runs but points sftp at a binary that does not exist.
