# Packaging the sshd Drop-in Play as a Role (docker-local, debian+rhel)

## Overview

The play built up over `handlers-notify.md`, `handlers-rescue.md` and `handlers-cleanup.md` lived in a single `site.yml`. That play renders an sshd `VersionAddendum` drop-in, validates it, checks the merged configuration, reverts in `rescue:`, cleans backups in `always:`, restarts the node through a handler and checks the live banner with `wait_for`. This exercise changes none of that task logic. It moves the sshd-specific part into a role named `sshd_dropin` and keeps everything else in the play. It runs on two docker-local nodes, `roles-sshd-node1` (Debian 12) and `roles-sshd-node2` (Rocky 9), grouped by their `os_family` label. The scaffolding and every task were carried over from `handlers-cleanup/` and are not re-derived here. `Verify SSH Configuration` stays an `ansible.builtin.command` task for the reason given in `handlers-notify.md`: no module validates sshd's merged configuration. What is new is where code lives and what that does to ordering: the role directory layout, the order in which a play runs `roles:` and `tasks:`, where role-provided variables sit in precedence, role argument validation, and the fact that handler names are shared across a whole play. One more lesson came out of the carry-over itself: variables from `group_vars` exist only after the inventory has been built.

## When a variable exists

The carry-over first tried to replace the hard-coded exercise name with `ansible_lab_name`/`ansible_lab_path`, defined in `group_vars/all.yaml` and referenced from three places. In `docker.yml`, the inventory plugin's `include:` filter failed with `'ansible_lab_name' is undefined`. A filter decides whether a container becomes a host at all. Group membership, and therefore which `group_vars` apply, is settled only after that decision, so no `group_vars` value can feed a filter. In `ansible.cfg`, the exercise's `ssh_common_args = -o UserKnownHostsFile={{ ansible_lab_path }}/known_hosts` was tested with an equivalent throwaway probe, whose setting `-o UserKnownHostsFile={{ lab_path }}/kh` reached `ssh` literally as `'UserKnownHostsFile={{' lab_path '}}/kh'`. `ansible.cfg` is plain configuration and is never rendered as Jinja2. Only the `path:` argument of the `known_hosts` task works with the variable, because task arguments are rendered per host just before each task runs, when the host's variables are complete. The final files keep the literal `roles-sshd` in `docker.yml` and `ansible.cfg` and the variable in `site.yml`.

## Role layout and lookup

A role is a directory under `roles/` beside the playbook, and Ansible finds each part by its location in that layout. `roles/sshd_dropin/tasks/main.yml` holds the block with its rescue and always sections, plus the post-block find and assert. `templates/banner.j2` holds the template. `meta/argument_specs.yml` declares the role's inputs. Each `main.yml` is a bare list, with no `hosts:` or `tasks:` key, because the directory already says what the list is. Inside the role, the unchanged `src: templates/banner.j2` resolved to the role's own `templates/` directory, and the output labels each role task as `sshd_dropin : <name>`. `ansible-lint`'s `var-naming[no-role-prefix]` flagged the three `register:` names inside the role. A registered variable becomes a host variable for the rest of the play, so two roles that both registered `backup_files` would overwrite each other's results. Prefixing gives `sshd_dropin_banner_result` and `sshd_dropin_backup_files`.

## Observable behavior

The unchanged carried-over play converged the fresh nodes with `ok=10 changed=4` on both (Write, Render, Verify, the restart), and the immediate rerun reported `ok=9 changed=0 skipped=1`. With the role under `roles:` and seeding under `tasks:` in one play, the converged nodes again reported `changed=0`, but all seven `sshd_dropin :` tasks printed before Collect and Write. After the nodes were recreated and `known_hosts` deleted, that layout failed on its first task: both hosts were `UNREACHABLE` with `Host key verification failed` (`ok=0 unreachable=1`), and neither `rescue:` nor `always:` ran. Seeding then moved into its own first play, with the role in a second play. A run of that layout without `flush_handlers` on fresh nodes showed the restart arriving too late. Node2 timed out after 31 seconds waiting for `Rocky` (`ok=9 changed=2 failed=1`). Node1 passed and got its restart only afterwards (`ok=11 changed=3`). The stock Debian banner `SSH-2.0-OpenSSH_9.2p1 Debian-2+deb12u10` already contains `Debian`, so node1's check could not fail. With the banners changed to `DebianX`/`RockyX` and the flush restored, a fresh run reported `ok=11 changed=3` on both and the rerun `ok=10 changed=0`. Commenting out `ssh_banner` in `rhel.yaml` after adding the argument spec failed node2 at `Validating arguments against arg spec 'main'` with `missing required arguments: ssh_banner` (`ok=3 failed=1`). Node1 continued to `wait_for` (`ok=11 changed=0`). The final layout, with the handler in the play, is traced in the worked example. Its rerun reported `ok=11 changed=0 skipped=1` on both, and `ansible-lint` passed at the `production` profile.

## Internal mechanism

A play runs `roles:` before `tasks:` regardless of the order the keys appear in the YAML, which is why the single-play layout tried to connect before seeding. With `known_hosts` already populated, nothing showed the problem. For handler flushing, `roles:` and `tasks:` behave as one stretch: the automatic flush comes only after the play's `tasks:`, not when the role ends. Without `meta: flush_handlers`, `wait_for` therefore ran against an sshd still serving its old configuration. Handler names are resolved across the whole play, as a localhost probe confirmed: a role task's `notify` ran a handler defined only in the play's `handlers:`. Role variables sit at two ends of the precedence order covered in `inventory-groups.md`. `defaults/main.yml` is below inventory `group_vars`, and `vars/main.yml` is above them. That was reasoned through as a prediction and not run: a `vars/` value would give both nodes the same banner, while a `defaults/` value would lose to each family's `group_vars`. `meta/argument_specs.yml` makes Ansible insert a validation task at the start of the role. It checks each option's `type` and `required` and fails the host before any task touches it.

## Design rationale

Seeding stays outside the role because it is controller-side preparation for any connection, not part of configuring sshd, and the separate first play guarantees it runs before anything connects. `ssh_banner` is declared `required: true` with no default. A silent default would let `wait_for` confirm that some banner was applied, never that the operator's intended one was. A missing value now stops the host at validation with an error that names the option. The handler moved out of the role and was renamed from `Restart Container` to `Restart SSH`. Its body, `community.docker.docker_container` with `restart: true` delegated to localhost, only works on container targets. As a play handler, the role's `notify: Restart SSH` becomes a contract that each play fills in for its own target, such as a systemd restart on the vagrant-local VMs. The name states what the role needs, not how one target does it. The `DebianX`/`RockyX` values are there so that the verification can actually fail.

## Edge cases

A connection failure is not a task failure. When Render was `UNREACHABLE`, the block's `rescue:` and `always:` did not run, and why was left open. `ansible-lint` flagged role-registered variables without the prefix, but it accepted `ssh_banner`, which the role reads and declares in its argument spec. That difference was not investigated. Play 2 still gathers facts by default, which the role does not need. One mid-session run was not from fresh nodes because an earlier unshown run had already converged them. The nodes were recreated before the figures above were taken.

## Worked example

Take freshly recreated nodes with `known_hosts` matching their keys and the final files. Play 1 runs Collect (`ok`, `changed_when: false`) and Write (`ok`, entries present). Play 2 gathers facts and enters the role. The validation task finds `ssh_banner` set to `DebianX` on node1 and `RockyX` on node2, both strings, and reports `ok`. Render finds no `10_banner.conf`, writes `VersionAddendum DebianX` (or `RockyX`) after `sshd -t -f` accepts it, makes no backup because the destination did not exist, and reports `changed`. Verify's merged `sshd -t` passes, and `changed_when` copies Render's `changed`, which queues `Restart SSH` for that host. The always find reads the directory under `become`, finds no backups, passes its `skipped_paths` assert, and the delete loop prints `skipping`. The post-block find and assert pass. Back in the play's `tasks:`, `flush_handlers` runs the play handler, printed as `RUNNING HANDLER [Restart SSH]` without a role prefix, which restarts both containers. `wait_for` then finds `RockyX` in node2's banner and `DebianX` in node1's, strings that only the active drop-in can produce. The recap is `ok=12 changed=3 skipped=1` on both nodes.
