# Privilege Escalation and Idempotent Package Install (docker-local, debian+rhel)

## Overview

This is the first exercise in the repo whose tasks change the managed nodes themselves. Every earlier task either only read state or, as with the `known_hosts` file in `inventory-hostkeys.md`, wrote to the controller. The goal is to have two packages present on two docker-local nodes, `packages-become-node1` (Debian 12) and `packages-become-node2` (Rocky 9). The first package is `tree`, which has the same name on both families. The second is the cron daemon, packaged as `cron` on Debian and `cronie` on Rocky. One play does this through the generic `ansible.builtin.package` module, escalating to root only where needed, and then proves the result with `package_facts` and `assert`. Inventory comes from the `community.docker.docker_containers` plugin, grouped by an `os_family` container label exactly as derived in `inventory-dynamic.md`. Host-key trust comes from a seeding play in `site.yml` that follows `inventory-hostkeys.md`. Both mechanisms are cited here, not re-derived.

## What `present` means and what `package` abstracts

A task declaring `state: present` describes a target state, not an action. The module first looks at what the node already has and acts only if the package is absent. The status it reports describes what it had to do: `changed` when it installed, `ok` when it found the package already there. That comparison-then-action is the whole idempotency argument for this exercise. A second identical run finds every package present and reports `ok`.

`ansible.builtin.package` is a proxy. With the default `use: auto` it reads the `ansible_pkg_mgr` fact and hands its arguments to `ansible.builtin.apt` on node1 or `ansible.builtin.dnf` on node2. Underneath, `apt` sits on `dpkg` and `dnf` sits on `rpm`. The higher layer fetches from repositories and resolves dependencies, and the lower layer keeps the installed-package database. `package` does not translate package names: a task with `name: cron` would fail on node2, because dnf has no package of that name. Choosing the manager is abstracted. Naming the package is not.

## Observable behavior

A fresh run of the final `packages.yml` against freshly created containers reports `changed=2` per host, from the `tree` and cron tasks, and the assertions pass. The immediate second run reports `changed=0` on both hosts. On node1, the module's bootstrap installs `python3-apt` during the first run, yet the task that declares `python3-apt` reports `ok`. No status line or recap count shows that install.

Earlier runs in the session showed three different stopping points on node1. Without `become`, the task FAILED during apt's bootstrap with `apt-get update` and `E: List directory /var/lib/apt/lists/partial is missing. - Acquire (13: Permission denied)`. On node2 the same task FAILED with dnf's `This command has to be run under the root user.` Both are FAILED, not UNREACHABLE, because login succeeded and the module started before hitting the permission wall. With `become`, `--check --diff` reported `changed` on node2. On node1 it FAILED with `python3-apt must be installed to use check mode. If run normally this module can auto-install it`. The first real run with `become` reported `changed` on both hosts. Its diff on node1 named only `tree`, though `python3-apt` had also been installed and `/var/lib/apt/lists/` repopulated. Installing `cron` on Debian pulled in 16 packages, including the `exim4` mail server, because apt installs Recommends by default. `cronie` on Rocky installed alone. Re-running `site.yml` against recreated containers left its `known_hosts` task `ok`, because both images generate their host keys at build time and the containers came back on the same IPs.

## Internal mechanism

Ansible still logs in over SSH as the unprivileged `ansible` user. `become: true` makes the `ansible.builtin.sudo` become plugin run the module process as `become_user`, which defaults to root. No password prompt is needed because each image's `/etc/sudoers.d/ansible` grants `ansible` passwordless sudo. Installing a package writes into `/var/lib/dpkg/` or the rpm database under `/var/lib/rpm/`, which only root may write, so every install task needs escalation. `package_facts` only reads those databases, and they are world-readable, so it runs unescalated.

The `apt` module talks to apt through its Python bindings, the `python3-apt` package, which the Debian image does not ship. When the bindings are missing in a normal run, the module bootstraps them by refreshing the cache and installing `python3-apt`, and only then evaluates its own `name`/`state` arguments. In check mode it refuses instead. Installing the bindings would modify the node, and without them it cannot query apt at all, so even a prediction is impossible. `package_facts` with `manager: auto` also depends on these bindings on Debian. On Rocky it reads through `python3-rpm`, which is already present as a dependency of dnf. The per-family names live in `group_vars`: `cron_package` is `cron` or `cronie`, and `package_mngmt` is `python3-apt` or `python3-rpm`. Group membership from the dynamic inventory picks which file applies, by the inheritance described in `inventory-groups.md`.

`register` stores a module's return exactly as returned. `package_facts` returns `packages` nested under `ansible_facts`, so the registered path is `package_facts_result.ansible_facts.packages`. Because the data comes back under `ansible_facts`, Ansible also merges it into the host's facts. As established in `inventory-dynamic.md`, the `is defined` test asks whether a lookup produced a value without using it. What is new here is that this holds for the whole chain: if any intermediate key is missing, the expression is simply false and raises no error.

## Design rationale

`become` sits on each install task, not on the play. That is least privilege: only the tasks that write the package database run as root. Play-level `become` would also escalate the implicit Gathering Facts task and `package_facts`, neither of which needs it.

The per-family names live in `group_vars` because the playbook expresses intent through a variable name and each family supplies its own value. It works like an interface and its implementations. A third family means adding one `group_vars/<family>.yaml` that defines the variables, with no edit to `packages.yml`. The cost has the same shape: a family that forgets to define a variable fails at the task that uses it.

The explicit bindings task exists to declare a dependency the verification relies on. It doesn't make anything more visible. Without it, `package_facts` on Debian worked only because an earlier install task had bootstrapped `python3-apt` as a side effect. Reordering the tasks so that `package_facts` ran first would make it fail on a fresh Debian node, because nothing would have installed the bindings yet; the explicit task removes that ordering dependency. It does not make a check-mode run on a fresh node1 possible, because the bindings task is itself an `apt` call and refuses in check mode for the same reason. As observed, the task still reports `ok` on a fresh node1, because the bootstrap completes before the state check. Its value is the declaration and the ordering guarantee, not a `changed` line. Naming `python3-rpm` for Rocky rather than leaving the list empty keeps the interface uniform and makes node2's equivalent dependency explicit at the cost of one `ok`.

## Edge cases

`package_facts` returns a snapshot taken when it runs. Placed before the install tasks, it captured a database without `tree` or `cron`, and the assert failed on a fresh run even though both packages were installed moments later. The snapshot has to come after everything it is used to verify. A defined-ness test on a mistyped path fails safely with `is defined`, as the session's first assert did when it read `package_facts_result.packages[...]`. With `is not defined`, for example when proving a removal, the same typo would pass while the package is still installed. So a path should be proven against a known case before a defined-ness test on it is trusted.

## Worked example

Start from two fresh containers, already trusted by `site.yml`. Node1 has neither `python3-apt`, `tree` nor `cron`. Node2 has `python3-rpm` but neither `tree` nor `cronie`. Gathering Facts runs unescalated on both and sets `ansible_pkg_mgr` to `apt` on node1 and `dnf` on node2.

The first task resolves `package_mngmt`. On node1 `package` hands `name: python3-apt` to `apt` as root. `apt` finds its bindings missing, refreshes the empty cache, installs `python3-apt`, and then checks its argument. The package is now present, so it reports `ok`. On node2 `dnf` finds `python3-rpm` present and reports `ok`. The second task installs `tree` on both and reports `changed` twice. The third resolves `cron_package` to `cron` on node1, which installs with its 16-package Recommends set, and to `cronie` on node2. Both report `changed`. `package_facts` then reads each database unescalated, and the snapshot now contains both names. The assert looks up `cron` and `tree` on node1 and `cronie` and `tree` on node2 under `ansible_facts.packages`, and both pass. The recap reads `changed=2` per host. A second run repeats every comparison, finds every package present, reports `ok` throughout, and ends with `changed=0`.
