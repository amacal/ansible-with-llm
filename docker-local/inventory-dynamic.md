# Docker Dynamic Inventory (docker-local)

## Overview

Every earlier docker-local exercise declared its hosts by hand in an `inventory.ini`, and `inventory-basics.md` already named the weakness: a static file records bridge IPs that stop being true the moment containers are recreated in a different order. This exercise replaces that file with the `community.docker.docker_containers` inventory plugin, which asks the Docker daemon for the list of containers and their addresses every time Ansible loads the inventory. The managed nodes are `inventory-dynamic-node1` (Debian 12, labelled `os_family=debian`) and `inventory-dynamic-node2` (Rocky 9, labelled `os_family=rhel`). A third container, `inventory-dynamic-node3`, was started without a label and left running as a standing negative check. The playbook `site.yml` seeds host keys, gathers facts over SSH and asserts that each node's distribution and Python interpreter match its family's `group_vars`.

## The plugin configuration file

An inventory plugin is driven by a YAML configuration file rather than a host list. `ansible.cfg` points `inventory =` at `docker.yml`, and the default `auto` inventory plugin reads its top-level `plugin:` key and hands the file to `community.docker.docker_containers`. The plugin accepts the file only if its name ends in `docker.yml` or `docker.yaml`. Under the name `inventory.yml`, the `auto`, `yaml` and `ini` parsers each declined it in turn with a warning, and the result was an empty `@all`/`@ungrouped` with exit code 0. The same warnings-plus-exit-0 behavior described in `inventory-basics.md` applies.

The plugin lists every container on the daemon, and this daemon is shared with the whole host (38 containers at the time). `filters` is an ordered list of `include`/`exclude` Jinja2 conditions in which the first match decides, and a container that matches nothing is *included*. A list containing only `include` entries therefore restricts nothing. The allow-list form ends with `exclude: True`, which flips the fall-through default to "out". The final file excludes containers whose `os_family` label is undefined, then those whose label value is not `debian` or `rhel`, then includes names starting with `inventory-dynamic-`, then excludes everything else.

## Observable behavior

`ansible-inventory --graph` lists exactly `@debian` holding node1 and `@rhel` holding node2. node3 is absent although it is running. `ansible-inventory --host inventory-dynamic-node1` showed `ansible_ssh_host: 172.17.0.3` and `ansible_ssh_port: 22` before the swapped recreation (`172.17.0.4` after). The first `ansible-playbook site.yml` run reported `ok=4 changed=1` per node, the `changed` coming from the `known_hosts` write, and the next run reported `changed=0`. After the interpreter assert was added the RECAP became `ok=5 changed=0`. Once the containers were recreated in swapped order, the next run reported `changed=1` per node and the run after it `changed=0`, with no file in the exercise edited.

## Internal mechanism

With the default `connection_type: docker-api`, the plugin sets `ansible_connection: community.docker.docker_api` and `ansible_host` to the container name, so modules run through the daemon socket and SSH is never used. Switching to `connection_type: ssh` makes the plugin set `ansible_ssh_host` to `default_ip` (127.0.0.1) and `ansible_ssh_port` to the host-side published port (32779 for the `-p 0:22` mapping). Neither is reachable from the devcontainer, which talks to the node on its bridge IP at port 22. The `host` option of `ansible.builtin.ssh` reads the variables `inventory_hostname, ansible_host, ansible_ssh_host` in that order, and when several are defined the later one wins. A composed `ansible_host` would therefore be silently overridden, so `compose` must set `ansible_ssh_host` and `ansible_ssh_port` themselves. `compose` runs after the plugin's own variables are set, so its values replace them. Each `compose` value must be a string holding a Jinja2 expression. `ansible_ssh_host: docker_networksettings.IPAddress` reads the inspect data, and `ansible_ssh_port: "22"` is a string that evaluates to the integer 22.

The inspect data is available to `compose`, `groups` and `filters` under slugified top-level names (`docker_config`, `docker_networksettings`, ...). With `verbose_output: true` it is also exposed as host variables, which made it possible to discover these paths with `--host`. `keyed_groups` with `key: docker_config.Image` and `prefix: image` generated `image_ansible_node_debian`, because generated group names have every character outside letters, digits and underscore replaced by `_`. `groups` names the group exactly and uses a condition only to decide membership, which is why `debian` and `rhel` come from `groups:` on `docker_config.Labels.os_family`. Groups exist once the inventory has loaded. Only then are `group_vars/` files next to the inventory source matched to groups by exact name, as described in `inventory-groups.md`, so it does not matter that a plugin created the group.

## Design rationale

The SSH connection mirrors how a real VM is managed and keeps the host-key trust work from `inventory-hostkeys.md` meaningful. The cost is that a `known_hosts` file has to be seeded and maintained, which `docker-api` avoids entirely. Group membership comes from an explicit label rather than the image name, so that a renamed or new image cannot silently change a host's family. The cost is that every `docker run` has to remember the label. `strict: True` turns an invalid expression into a failure of the whole inventory source instead of a host with a quietly wrong variable. An empty inventory makes a playbook do nothing, while a wrong address makes it act somewhere else. The cost is that one bad entry removes every host, which the filter ordering then had to guard against. The seeding play is a close adaptation of the one in `inventory-hostkeys/site.yml`, with `inventory_hostname` (equal to the container name here) replacing the hand-maintained `container_name` and `ansible_ssh_host` replacing `ansible_host`.

## Edge cases

Three misconfigurations produced no error at all. With `strict: false`, the bare integer `ansible_ssh_port: 22` was skipped and the plugin's 32779 remained. The misspelled option `struct: True` was ignored as an unknown key. A `gather_subset` item written as the single string `"!all,!min"` is not split on commas, so `min` was still collected; the playbook still passed, and this was found only by listing the gathered fact keys. Splitting it into separate `!all` and `!min` items and adding `python` made the dependency explicit. Without `python` in the list, the interpreter assert would stop with an undefined-key error, not `Assertion failed`. Under `strict: True`, an unlabelled container that passed the filters made `docker_config.Labels.os_family` fail to evaluate in `groups`, and the whole inventory came back empty with a warning and exit 0. A first fix, `exclude: docker_config.Labels.os_family not in [...]`, failed the same way, because the attribute lookup happens before `not in` is evaluated. The `is not defined` test checks whether the lookup produced a value without using it. Placed first, it excludes node3 before the value check is ever reached.

## Worked example

Start from node1 at 172.17.0.3 and node2 at 172.17.0.4, with the per-exercise `known_hosts` holding the Debian key on `.3` and the Rocky key on `.4`. Both containers are removed and node2 is started first, so node2 (Rocky) now holds 172.17.0.3 and node1 (Debian) holds 172.17.0.4. Nothing in the exercise directory is edited. When `ansible-playbook site.yml` starts, the plugin queries the daemon and finds three exercise-prefixed containers. node3 has no `os_family` label and is excluded by the first filter. node1 and node2 pass through to `include`, `compose` gives node1 `ansible_ssh_host: 172.17.0.4` and node2 `172.17.0.3`, and `groups` places them in `debian` and `rhel`, which pull in their interpreters and expected distributions from `group_vars`.

The first task runs `docker_container_exec` on the controller against container `inventory-dynamic-node1` and reads the Debian public key, with `changed_when: false`. The `known_hosts` task then looks for lines named `172.17.0.4`, finds one holding the Rocky key, replaces it with the Debian key and reports `changed`. The same happens for node2 on `.3`. ssh now dials 172.17.0.4 for node1 and finds the matching Debian key, so `setup` collects the distribution and python facts. `Debian` equals the `distribution` from `debian.yaml`, and the executable `/usr/bin/python3.11` equals `ansible_python_interpreter`, so both asserts pass and the RECAP shows `ok=5 changed=1` per node. On the immediate second run both `known_hosts` lines already hold the right keys, and the RECAP is `ok=5 changed=0`.
