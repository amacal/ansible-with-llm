# Jinja2 Templates and --diff (docker-local, debian+rhel)

## Overview

Every earlier exercise in this repo either only read state from a managed node or installed packages on it. This one makes a playbook write a file whose content is declared in the playbook and differs per host. The file is a cron entry at `/etc/cron.d/mycron` on two docker-local nodes, `files-templates-node1` (Debian 12) and `files-templates-node2` (Rocky 9). It contains a comment naming the node's distribution and major version, a blank line, and one cron line whose schedule comes from that family's `group_vars`. One template source on the controller therefore produces two different files on the two nodes. The cron daemon it depends on is installed per family exactly as in `packages-become.md`, and inventory and host-key trust follow `inventory-dynamic.md` and `inventory-hostkeys.md`. The session also settled a question that `inventory-hostkeys.md` left open, about concurrent writes to the controller's `known_hosts` file, so these notes run somewhat past the usual 1400-word ceiling. They combine the template mechanism with that separate concurrency finding.

## Idempotency for a file

A task that declares "this file must have exactly this content" needs two things to compare: the desired content, which only the controller knows, and the actual file on the node. If they are equal the task reports `ok`, and otherwise it writes the desired content and reports `changed`. A missing file simply counts as unequal. Because the desired content differs per host, the source cannot be the final text. It is a template, meaning literal text with `{{ ... }}` expressions inside it, and it is rendered once per host with that host's variables. Those are its `group_vars`, chosen by group membership as in `inventory-groups.md`, and its gathered facts. Rendering happens on the controller. The controller holds the template file and every variable, and the node images ship only `sshd` and `python3`, with no Jinja2 library.

Shipping the whole rendered text to the node on every run just to discover that nothing changed would be wasteful. So each side computes a SHA1 checksum, the two are compared, and the content travels only when they differ. The module documentation also notes that a template containing the render date reports `changed` on every run. The date changes the rendered text, so the checksums never match. The general rule is that any template input which varies between runs, and does not describe the desired state, breaks idempotency.

## Observable behavior

A run with `--check --diff` against nodes that do not yet have the file reports the template task `changed` on both. Its diff starts from nothing (`@@ -0,0 +1 @@`), and the after side for node2 reads `# Rocky 9`. The after side's label is a path under `/home/vscode/.ansible/tmp/` on the controller, which is the rendered file sitting there before any transfer. That check-mode run passed even though the task at that point had no `become`. A real run would have failed on permissions. Check mode reported a clean `changed` for an operation that could not succeed.

On freshly recreated containers, the final playbook reports `changed=2` per host, from the cron package and the template. The seeding tasks report `ok`, because the IPs and the image host keys were unchanged. The immediate second run reports `changed=0` on both hosts. On the nodes, `cat -A` shows `root:root`, `-rw-r--r--`, the per-family comment and schedule, and the blank line copied literally.

The two kinds of drift look different in `--diff`. When a line was appended by hand on node1, the next run reports `changed` with a text diff whose before side is `/etc/cron.d/mycron` and which removes the extra line, and the file's mtime moves. When node2's file was `chmod 666`ed with its content untouched, the next run reports `changed` with no text diff at all. Instead it prints a small JSON-shaped object going from `"mode": "0666"` to `"0644"`, and the mtime stays put. Changing only `cron_schedule` in `group_vars/rhel.yaml` from `30 1 * * 1` to `45 1 * * 1` leaves node1 `ok` and gives node2 a diff with exactly one `-` line, one `+` line, and two unchanged context lines.

## Internal mechanism

`ansible.builtin.template` has a corresponding action plugin, the controller-side half of the task. It renders `src`, which a relative path resolves from `templates/` next to the playbook. It then compares the result's checksum with the one from the file at `dest` on the node. When the checksums differ, the rendered file is uploaded into a temporary directory under the login user's home, `~ansible/.ansible/tmp/`, which needs no privilege. It is then moved into `/etc/cron.d` and `chown`ed to `root:root`, and those two steps need root, which is why the task carries `become: true`. Check mode stops after the comparison. It only reads, and `ansible` may read `/etc/cron.d`, so check mode never reaches the steps that would have failed. Owner, group and mode are separate pieces of declared state, each compared against the actual file independently of the content checksum. When only the mode differs, nothing is transferred and only a `chmod` runs. That explains both the attribute-shaped diff and the unchanged mtime. When `mode` is left undeclared, an existing file keeps whatever mode it has.

`mode` has to be quoted. YAML parses an unquoted `mode: 644` as the decimal integer six hundred forty-four, and Ansible then uses that number directly. Converting that number to octal, the base Unix permissions are read in, shows what the node would actually receive.

$$644_{10} = 1 \cdot 512 + 2 \cdot 64 + 0 \cdot 8 + 4 = 1204_8$$

Read as permissions, that leading `1` is the sticky bit and the `2` leaves the owner with only write access, so the file comes out as something no one intended. The string `'0644'` lets Ansible do the octal conversion itself, so the permission means what the author intended. The facts the template reads come from an explicit `ansible.builtin.setup` task with `gather_subset: distribution`, placed after the host-key seeding. Fact gathering is that same module run as an implicit first task, so setting `gather_facts: true` on this play would try to connect before the keys were trusted.

## Design rationale

One template with the differences held in variables keeps a single file to maintain, and every per-family difference becomes visible in `group_vars`. The tradeoff is that a template is only idempotent if its inputs are stable, and forcing structurally different files into one template can become over-engineering. Separate static files with `ansible.builtin.copy` are the better choice when the variants have little in common. The distribution line uses facts rather than the `distribution` value in `group_vars`, because a fact describes the actual node, while a group value only records what the group was assumed to contain. Verification uses a separate `ansible.builtin.stat` task registered as `cron_stat_result`, whose `stat.mode` is returned as a string. It does not reuse the template task's own return, which only reports what that module believed it set. The `stat` read is a second, independent observation. The asserts check `exists`, `mode == '0644'`, `uid == 0` and `gid == 0`. The assert was itself shown to fail: with node2 `chmod 666`ed, `--start-at-task "Verify CRON Job is Installed"` skips the repairing template task, and node2 fails on `cron_stat_result.stat.mode == '0644'`.

## Edge cases

The first real run failed on node1 with "Host key verification failed", although the `known_hosts` task reported `changed` for both hosts. The file held only node2's line. Both hosts' copies of that `delegate_to: localhost` task ran in parallel against one controller file. Each read the empty file, wrote a temp file with its own line, and renamed it into place. The second rename won, and both truthfully reported `changed`. The atomic rename prevents a corrupted file but not this lost update, which answers the question left open in `inventory-hostkeys.md`. The `throttle: 1` task keyword serializes the task. A single clean run proves nothing here, since earlier sessions passed by timing luck. The argument is structural: the second read cannot start before the first rename has finished. Separately, a fresh Rocky node has no `/etc/cron.d` until `cronie` is installed, while Debian ships the directory with `e2scrub_all`. `template` does not create parent directories, so the install task must come first. A misordering would fail only on Rocky.

## Worked example

Take a freshly recreated node2 and the final `site.yml`. The controller lists both containers through the dynamic inventory, and node2 lands in `rhel` through its `os_family` label. The `known_hosts` task, now throttled to one host at a time, finds the line for 172.17.0.4 already correct and reports `ok`. The package task resolves `cron_package` from `group_vars/rhel.yaml` to `cronie` and installs it as root, reporting `changed`, and the install creates `/etc/cron.d` containing `0hourly`. The `setup` task stores `distribution` as `Rocky` and `distribution_major_version` as `9`. The template's action plugin renders `# Rocky 9`, a blank line, and `45 1 * * 1 root /usr/bin/true` on the controller. The checksum from the node reports no file, so the plugin uploads the render to `~ansible/.ansible/tmp/`. The module, running as root, moves it to `/etc/cron.d/mycron` and sets `root:root` and `0644`, and the task reports `changed` with a three-line `+` diff. `stat` then reads mode `'0644'` and uid and gid `0`, and the assert passes, for `changed=2`. On the immediate second run, the package is present, the checksums match, and owner, group and mode all agree, so every task reports `ok` and the recap shows `changed=0`.
