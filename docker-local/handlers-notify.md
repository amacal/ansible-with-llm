# Handlers and Notify (docker-local, debian+rhel)

## Overview

A file on disk and the configuration a running process has loaded are two separate pieces of state, and this exercise is about keeping them in step. The playbook renders a one-line sshd drop-in, `/etc/ssh/sshd_config.d/10_banner.conf`, containing `VersionAddendum {{ inventory_hostname }}`, onto two docker-local nodes, `handlers-notify-node1` (Debian 12, OpenSSH 9.2p1) and `handlers-notify-node2` (Rocky 9, OpenSSH 9.9p1). Both images' main `sshd_config` has `Include /etc/ssh/sshd_config.d/*.conf`, so that line appends the node's own name to the banner sshd sends when a client connects on port 22. Writing the file alone changes nothing a client can see, because sshd reads its configuration only at startup. The banner changes only after sshd restarts, and the playbook must restart it exactly when the file changed and never otherwise. That conditional reaction is what a handler is for. Inventory, host-key seeding and the template task itself follow `inventory-dynamic.md`, `inventory-hostkeys.md` and `files-templates.md`. These notes run past the usual 1400-word ceiling on purpose, because the session combined four mechanisms that each needed their own trace: handler notification and flushing, the loss of pending handlers on host failure, `template`'s `validate` parameter, and a separate merged-configuration check whose results differed between the two OpenSSH versions.

## Handlers in plain terms

A handler is an ordinary task written in a separate `handlers:` section of the play instead of the `tasks:` list, and it never runs on its own. A normal task names it in its `notify:` keyword. When that task reports `changed` on a host, Ansible adds the handler to that host's set of pending handlers, and when the task reports `ok` nothing is added. The pending set is kept per host, and adding the same handler twice leaves it there once, so a handler runs at most once per host per flush however many tasks notify it. Ansible runs pending handlers automatically after the `tasks:` section has finished. The `ansible.builtin.meta` module with the free-form value `flush_handlers` runs them earlier, at a point the author chooses. From `files-templates.md` comes the one fact the whole mechanism rests on: `template` reports `changed` only when the rendered content's checksum differs from the file on the node, or when a declared `owner`, `group` or `mode` has drifted.

## Observable behavior

On freshly recreated containers, the playbook as it stood before the merged check was added reported `ok=5 changed=2` per host on the first run and `ok=4 changed=0` on the immediate second run; the final playbook, with the merged check, reported `ok=6 changed=2` and then `ok=5 changed=0` on the restoring run after the Subsystem test, on nodes that were not fresh. In both cases the two changes are the Render task and the `Restart Container` handler, and `RUNNING HANDLER [Restart Container]` appears between the flush task and `Ensure Banner is Applied`. Each container's `StartedAt` timestamp moves, and the raw banner on port 22 then reads `SSH-2.0-OpenSSH_9.2p1 Debian-2+deb12u10 handlers-notify-node1` and `SSH-2.0-OpenSSH_9.9 handlers-notify-node2`. On the second run no handler header appears. The flush task prints a `TASK [Run pending handlers]` header (twice, in this ansible-core version, for reasons the session did not establish) but no per-host line. It is never counted in the recap, because a meta task is not a module run against the host.

Under `--check --diff` on fresh nodes, the handler still runs at the flush and reports `changed`, with a diff from `"restarted": false` to `true`. `StartedAt` stays unchanged, because `community.docker.docker_container` supports check mode and only reports what it would do. This worked only after the `known_hosts` seeding task gained `check_mode: false`. Without it, check mode showed the seeding diff but wrote nothing, and the next SSH connection failed with "Host key verification failed".

## Internal mechanism

The handler is `community.docker.docker_container` with `name: "{{ inventory_hostname }}"`, `state: started` and `restart: true`, run with `delegate_to: localhost`. sshd is PID 1 in both images, and neither image has an init system, so restarting sshd means restarting the container. Only the Docker daemon, reached from the controller, can do that. `state: started` alone is a declaration that reports `ok` on a running container. `restart: true` forces a stop and start and reports `changed` every time, so taken alone that task is not idempotent. The playbook is idempotent only because the handler borrows its idempotency from the task that notifies it. On the second run Render's checksum and declared attributes match, so it reports `ok`, nothing is added to the pending set, and the restart never executes.

Verification is split in two, because a file and a process are different state. `template` guarantees the file. `ansible.builtin.wait_for`, delegated to `localhost` with `host: "{{ ansible_ssh_host }}"`, `port: "{{ ansible_ssh_port }}"`, `search_regex: "{{ inventory_hostname }}"` and `timeout: 30`, opens a TCP connection and reads the banner until that node's own name appears. Only that task can prove the running daemon loaded the new file.

Two guards protect the restart. The first is `validate: /usr/sbin/sshd -t -f %s`, a module argument of `template` (placed at task level it is read as a second module, and Ansible rejects the task with "conflicting action statements"). It runs on the managed node, as root, against the temporary file under `/home/ansible/.ansible/tmp/`, before the move into `sshd_config.d/`, and only when the checksum differs. A non-zero exit fails the task with `changed: false`, so nothing is notified and the destination is untouched. The second is `Verify SSH Configuration`, an `ansible.builtin.command` task running `/usr/sbin/sshd -t` with `become: true` and `changed_when: false`, placed between Render and the flush. It uses `command` because no module validates sshd's merged configuration. `validate` can only parse the drop-in on its own, and the merged view exists only once the file is already in place. `changed_when: false` keeps it from reporting `changed` on every run.

## Design rationale

The same first-run and second-run behavior could be had with `register` on Render and an inline restart task guarded by `when: <result> is changed`. The handler model is preferred for two reasons. Several tasks can notify one restart and it still happens once, and the restart is deferred to a single chosen point, here the explicit flush placed right before the check that depends on it. Its cost was demonstrated: a notification exists only inside the run that created it, and a host that fails a later task loses its pending handlers. The flush narrows that window to the tasks between Render and the flush. The only task there is `Verify SSH Configuration`, and there the loss is deliberate. If the merged configuration is invalid, the host fails and the restart into a broken configuration is dropped. `force_handlers` was considered and left off, since no other task sits in that window. That judgment holds only for the play's current shape, and a task inserted later between Render and the flush would reopen the window silently.

## Edge cases

When the flush was removed, `wait_for` ran before any restart and timed out on both hosts. The pending restarts were then discarded, and no `RUNNING HANDLER` appeared. The nodes were left with a correct file and an old daemon. Any later run would report Render `ok`, notify nothing, and fail at `wait_for` again (reasoned in dialogue; the nodes were recreated before such a run happened), and `--force-handlers` cannot help such a run because nothing is pending. Run with `--force-handlers` on the failing run itself, the restarts did happen after the failures. The run still reported `failed=1`, but the nodes converged, and the following run reported `changed=0`.

An invalid drop-in that reaches a restart kills PID 1 and stops the container. After that the playbook cannot recover the node, since `docker exec` and SSH both need it running. `validate` stopped a line with an unknown directive before it was written. After a failed merged check, the node is left split: the bad file on disk and the old configuration in memory, with nothing reverting the file. The checks have limits as well. `sshd -t` proves only that a configuration is acceptable to that sshd version, and `wait_for` proves only that the banner changed. Neither checks semantics, such as whether a referenced binary exists.

## Worked example

Start from both nodes converged, with `banner.j2` given a temporary second line, `Subsystem sftp /usr/lib/openssh/sftp-server`, which is Debian's sftp-server path. For node1 the render is two lines, its checksum differs from the one-line file on disk, and `validate` parses the temporary file alone. Nothing in it is invalid in isolation, so the file is moved into `sshd_config.d/` and Render reports `changed`, adding `Restart Container` to node1's pending set. `Verify SSH Configuration` then runs `sshd -t` on the merged configuration. The `Include` at the top of `sshd_config` reads the drop-in's `Subsystem sftp` first, and OpenSSH 9.2p1 rejects the main file's own definition at line 115 with "Subsystem 'sftp' already defined" and exit status 255. node1 fails, its pending restart is dropped, and its `StartedAt` does not move.

node2 follows the same steps up to the merged check, where OpenSSH 9.9p1 accepts the duplicate and keeps the first value it read, so the check passes. The flush restarts node2, and `wait_for` finds `handlers-notify-node2` in the banner, giving `ok=6 changed=2 failed=0`. Yet `sshd -T` now reports `subsystem sftp /usr/lib/openssh/sftp-server`, a path that does not exist on Rocky, where the binary is `/usr/libexec/openssh/sftp-server`. After the extra line was removed, the restoring run printed "sftp transfer mechanism failed" and "scp transfer mechanism failed" warnings for 172.17.0.4 while uploading the render. Ansible fell back to piping the file over SSH and reported Render `changed`, and both nodes restarted onto clean configurations. A run that was green for node2 had broken the file-transfer path Ansible itself prefers, because no check in the playbook looked at SFTP.
