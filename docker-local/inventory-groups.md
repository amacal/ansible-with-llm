# Multi-Group Inventory, group_vars and Precedence (docker-local, debian+rhel)

## Overview

This exercise takes the single-host inventory from `inventory-basics.md` and grows it to two managed nodes from different OS families: `inventory-groups-node1`, a Debian 12 container at `172.17.0.3`, and `inventory-groups-node2`, a Rocky Linux 9 container at `172.17.0.4`. Both images create the same `ansible` user and receive the same mounted key, so most of what Ansible needs to reach them is identical. The one value that genuinely differs by family is the Python interpreter. Debian 12's `python3` package provides `/usr/bin/python3.11`, while Rocky 9's package of the same name provides `/usr/bin/python3.9` and no 3.11 at all. Both Dockerfiles ask only for `python3`, so the path is decided by the distribution's default, not by anything the image author wrote.

The intuition this exercise builds is that a variable has a natural owner. The address belongs to one host, the user and key belong to every host, and the interpreter belongs to every host of one OS family and major version. The exercise moves each value out of the host lines and into the group that owns it, then deliberately makes several sources compete for the same variable to observe which one wins. Everything stays read-only on the managed nodes, as in the previous exercise.

## Where group variables come from

Ansible attaches variables to a group by looking for a `group_vars/` directory next to the inventory file (and also next to the playbook, which in this exercise is the same directory). Inside it, a file named after a group, such as `rhel.yaml`, contributes its variables to every member of that group as if they had been typed on each host line. Two conditions must hold before any value in such a file is considered. First, the file's extension must be on the `YAML_FILENAME_EXTENSIONS` allow-list (`.yml`, `.yaml`, `.json`, or no extension). A file outside the list is skipped without any error or warning. Second, the file's top-level content must be a YAML mapping, so that it can be merged into the host's existing variables key by key. The INI-style line `ansible_python_interpreter=/usr/bin/python3.9` is valid YAML, but YAML reads it as one plain string, because only `: ` (colon then space) creates a key-value pair. Merging a string into a dict is impossible, and Ansible stops with a hard error.

## Observable behavior

`ansible-inventory --graph` shows `@all` as the root, with `@ungrouped` (empty), `@debian` holding `node1` and `@rhel` holding `node2` beneath it. When the Rocky interpreter sat in `group_vars/rhel.ini`, `ansible-inventory --host node2` listed only `ansible_host`, `ansible_user` and `ansible_private_key_file`, with no interpreter and no message. Renaming the file to `rhel.yaml` without changing its content produced `failed to combine variables, expected dicts but got a 'dict' and a '_AnsibleTaggedStr'`. After rewriting the line with `: `, the interpreter appeared. Once every shared value was in `group_vars/all.yaml` and each interpreter in its family file, `--host` reported exactly the same four variables per host as the original all-inline inventory.

Adding `ansible_python_interpreter: /usr/bin/python3` to `all.yaml` changed nothing for either host. A host-line `ansible_python_interpreter=/usr/bin/python3.9` on `node1` made `--host node1` report `/usr/bin/python3.9`. An ad-hoc `ping` then returned `FAILED!` for `node1` with `rc: 127` and `/bin/sh: 1: /usr/bin/python3.9: not found`, while `node2` returned `SUCCESS`. An earlier ping, before host keys were accepted, had returned `UNREACHABLE!` for both nodes with `Host key verification failed`. The final `site.yml` reports `ok=3 changed=0 failed=0` for both hosts on two consecutive runs. With `distribution: RedHat` in `rhel.yaml`, `node2` reported `ok=1 failed=1`.

## Internal mechanism

Inventory parsing first establishes membership: `node1` is in `debian` and `all`, and `node2` is in `rhel` and `all`. Ansible then gathers every applicable variable source and settles conflicts by depth. Along a host's path from `all` down to its own group, a child group's value overrides its parent's, so `all` is the weakest group-level source and applies only when nothing deeper sets the variable. A variable on the host's own line overrides every group. For `node1`, `all.yaml` supplies `/usr/bin/python3` and `debian.yaml` supplies `/usr/bin/python3.11`. With no host-line value, `debian` wins. `ansible-inventory --host` performs exactly this resolution without opening any connection, which is why it can display a path that does not exist on the node.

As traced in `inventory-basics.md`, the SSH login comes first and the module is then copied over and launched with the resolved interpreter. A failure before login is `UNREACHABLE`, and no module code runs. A failure after login, such as a missing interpreter (exit code 127 from `/bin/sh`), is `FAILED`. In `site.yml`, the implicit Gathering Facts task records the Python that actually ran it under `ansible_facts['python']['executable']`. The second assert compares that against `ansible_python_interpreter`, closing the loop between resolved value and actual execution. The first assert compares the `distribution` fact against a user-defined variable, `distribution`, that each family's group file sets. As recorded in `inventory-basics.md`, a host whose task fails is removed from the rest of the play, which is why `node2`'s second assert was neither run nor counted as skipped.

## Design rationale

Grouping values by owner makes inventory changes cheap and safe. A new Rocky 9 host needs only a name and an `ansible_host`, and it inherits the right user, key and interpreter by membership. A changed key path or interpreter is one edit in one file. With values copied onto every host line, a missed line leaves one host with a stale value, and nothing reports it until that host is run against and fails, as `node1` did with `rc: 127`.

The two asserts check different things on purpose. The interpreter assert checks the result: the value that actually executed modules. The distribution assert checks the input: that the host was filed in the group whose assumptions fit it. Asserting on `distribution` (`Rocky`) is stricter than `os_family` (`RedHat`, shared by Rocky, AlmaLinux, CentOS and RHEL). An AlmaLinux node added to `[rhel]` would fail it. That is acceptable, because the group's values encode a specific distribution and version. User-defined variables avoid the `ansible_` prefix, which Ansible uses for its own connection and magic variables. The `/usr/bin/python3` value in `all.yaml` is currently overridden for every host and acts only as a fallback for a host outside both families.

## Edge cases

The silent skip of a misnamed `group_vars` file is the most dangerous case here, because the only symptom is a variable that is quietly absent. A precedence experiment is only conclusive if each competing source carries a distinct value. While the host line and `all.yaml` both said `/usr/bin/python3`, the result could not distinguish the two. Sibling-group conflicts, where one host is in two same-depth groups that both set a variable, did not arise here. Ansible settles those alphabetically by group name unless `ansible_group_priority` is set. A future Rocky 10 node in `[rhel]` would receive `/usr/bin/python3.9` and fail at Gathering Facts with `FAILED` and `rc: 127`. The structural fix discussed was `rhel9` and `rhel10` child groups under `[rhel:children]`, keeping shared values in `rhel.yaml`, but it was not built. Recreated containers also needed their host keys accepted by hand, the still-deferred host-key topic.

## Worked example

Start from the final group files and add `ansible_python_interpreter=/usr/bin/python3.9` to `node1`'s host line. Three sources now offer `node1` an interpreter: `all.yaml` with `/usr/bin/python3`, `debian.yaml` with `/usr/bin/python3.11`, and the host line with `/usr/bin/python3.9`. Walking the ladder, `debian` overrides `all`, and the host line overrides both. `ansible-inventory --host node1` therefore reports `/usr/bin/python3.9`. Because `node1` is not in `rhel`, that string can have come only from the host line. `node2` is untouched and still resolves to `/usr/bin/python3.9` through `rhel.yaml`.

Now run `ansible all -m ansible.builtin.ping`. For `node2`, SSH logs in as `ansible` at `172.17.0.4`, the module runs under Python 3.9 and returns `pong`, so the result is `SUCCESS`. For `node1`, SSH logs in at `172.17.0.3` just as successfully, so it is not `UNREACHABLE`. Ansible then asks `/bin/sh` to launch the module with `/usr/bin/python3.9`, which Debian 12 does not have, and the shell exits with 127. The result is `FAILED`, with `module_stdout` saying `/usr/bin/python3.9: not found`. Remove the host-line value and the ladder falls back to `debian.yaml`. Gathering Facts in `site.yml` now runs under `/usr/bin/python3.11` and records that as `python.executable`. Both asserts hold, and the recap reads `ok=3 changed=0` on that run and on the next.
