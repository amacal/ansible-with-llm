# Orphaned Backup Cleanup with find and loop (docker-local, debian+rhel)

## Overview

`handlers-rescue.md` left a mess behind in `/etc/ssh/sshd_config.d/`. Every run of the play that changed the banner drop-in left a `10_banner.conf.<pid>.<YYYY-MM-DD@HH:MM:SS>~` backup next to it. A run that failed at `validate` also left one, but the failed result carried no `backup_file` key, so nothing in the play could name that file. This exercise makes the play delete those backups itself. It runs on two docker-local nodes, `handlers-cleanup-node1` (Debian 12) and `handlers-cleanup-node2` (Rocky 9), grouped by their `os_family` label. The scaffolding (`ansible.cfg`, the docker inventory plugin config, `group_vars`, host-key seeding) and the whole block/rescue structure, including the merged `sshd -t` check, the restart handler and the `wait_for` banner check, were carried over from `handlers-rescue/` and are not re-derived here. Verify stays an `ansible.builtin.command` task for the reason given in `handlers-notify.md`: no module validates sshd's merged configuration, and `validate` sees only the drop-in on its own. Three things are new. The banner text now comes from a per-group variable so that runs can be made to change or fail on purpose. The block gained an `always:` section that finds and deletes every backup. And a second find with an assert after the block checks the result independently. The new mechanisms are `ansible.builtin.find`, the `loop` keyword with `loop_control`, and `always:`. The exercise also hits one cross-target difference in directory permissions, which turned out to be its most instructive part. These notes run slightly past the usual 1400-word ceiling because the three new mechanisms each interact with the carried-over block/rescue paths, and each path needed its own observed figures.

## Finding names the play never knew

The template module saves the old destination before it runs `validate`, as `handlers-rescue.md` established from the backup a validate failure left behind. The backup name contains the PID of the module's process on the node and the node's clock to the second, and the controller sees neither. The only reliable way to find these files is therefore to look at the directory and select them by shape. `ansible.builtin.find` does exactly that. It takes `paths` (the directories to search) and `patterns` (shell globs matched against each file's basename), and it returns `files`, a list of stat-style dictionaries each holding a `path`, along with `matched` and `skipped_paths`. It only reads, so it never reports `changed`, and its documentation lists check mode support as full. The pattern settled on was `10_banner.conf.*~`. The fixed prefix marks the file as this play's own, the trailing `~` marks it as a template-module backup, and the `*` covers the PID and timestamp. The broader `10_banner.conf.*` would also match package-manager leftovers such as `10_banner.conf.rpmnew` or `10_banner.conf.dpkg-old`, and `*~` would take any editor backup in the directory. The `loop` keyword then turns one `ansible.builtin.file` task with `state: absent` into one call per element of `files`, with the current element bound to `item`. Because each element is a dictionary rather than a string, the path is `item.path`, and `loop_control.label: "{{ item.path }}"` replaces the whole stat dictionary that was otherwise printed on every iteration line.

## Observable behavior

Before the cleanup existed, node1 had collected three backups: `.68.` holding `Debian Banner`, `.55.` holding `Debian2` (the orphan from an invalid-quotes run at 12:30:12), and `.101.` holding `Debian2`. Node2 had `.165.`, `.153.` (the orphan) and `.308.` with the Rocky equivalents. The first version of the cleanup ran both finds without `become`, while the delete task already had it. Node1 listed and deleted all three backups and reported `ok=10 changed=1`. Node2's find succeeded but put the directory into `skipped_paths`, so the guard assert failed and node2 ended at `ok=5 failed=1` with its backups untouched. With `become` added to both finds, the next run deleted node2's three backups (`ok=10 changed=1`). Node1 had nothing left, so its delete task printed `skipping` (`ok=9 changed=0 skipped=1`). The immediate rerun reported `ok=9 changed=0 skipped=1` on both hosts. A valid change of `ssh_banner` to `Debian1`/`Rocky1` reported `ok=11 changed=4` on both: Render, Verify, Delete removing the single fresh backup, and the restart. Its rerun was again `changed=0 skipped=1`. An invalid value with an unbalanced quote produced `ok=5 changed=1 failed=1 skipped=2 rescued=1` on both nodes. The one change was the deletion of the orphan created a moment earlier, and the find and assert after the block never printed. Repeating that invalid run gave the same recap, with a new orphan created and deleted again. The final converge back to `Debian`/`Rocky` reported `ok=11 changed=4` on both. Its own rerun was not captured. The zero-change evidence comes from the two earlier reruns, which used the identical `site.yml`.

## Internal mechanism

An empty loop does not run the module at all. When `files` is empty, the looped task has nothing to iterate over, and Ansible reports it as `skipping`, not `ok`, which is why the second runs show `skipped=1` alongside `changed=0`. The `when: backup_files.files is defined` guards on the delete task and on the final assert are redundant, because `find` returns `files` on every successful run, but they are harmless. The cross-target split comes from directory modes. On Debian `/etc/ssh/sshd_config.d/` is `drwxr-xr-x root`, so the unprivileged `ansible` user can list it. On Rocky it is `drwx------ root`, so the same user cannot. `find` treats an unreadable path as skipped, not as an error: it returns success with `matched` at zero and the path recorded under `skipped_paths`. Deleting a file is a write to its directory, so `file state=absent` needs `become` on both families, even where listing works without it. `always:` runs after the block, and after `rescue` if it ran, whatever happened in either, including a rescue that ends in `ansible.builtin.fail`. The host is removed from the play only once the whole block construct has finished. That is why the orphan from a validate failure is deleted in the same run, while the tasks after the block never run for that host.

## Design rationale

The cleanup belongs in `always:` because it is the only place that runs on the failure path. Plain tasks after the block would leave every validate-failure orphan in place until some later successful run. A `shell: rm -f` with the glob was rejected under the hard constraint, and the technical reason behind the rule is visible in the recaps. `rm -f` reports `changed` on every run. If that is silenced with `changed_when: false`, a run that deleted three orphans and a run that deleted nothing look identical. The looped `file` task gives one `changed` line per real deletion and `skipping` when there is nothing to do. The two asserts guard against a trap the Rocky node exposed: a cleanup whose find quietly saw nothing would also pass a plain "zero matches" assert. Checking `skipped_paths | length == 0` makes the assert prove that the directory was actually read, not only that nothing was found. The retention policy is to delete every backup at the end of every run, including the one a successful change just made. The node keeps no history. The record of the previous value lives in the git history of `group_vars`, and in `--diff` output if a run used it, so a rollback means rerunning the play with the old value. Keeping the newest N backups, or anything younger than an age, was discussed only as a contrast. A validate-failure orphan costs nothing under either policy, because its content equals the live file. The variable replaced an early proposal to put a timestamp into the template. A timestamp would change the rendered content on every run, so the play could never reach zero changed.

## Edge cases

While an invalid value stays in `group_vars`, every run reports one change, the deletion of the orphan that the same run created, and fails afterwards. That is a property of a persistently failing input, not an idempotency defect. Changing the banner text also changes what `Ensure Banner is Applied` must search for. The first run with the new variable timed out after 31 seconds on both nodes because `search_regex` still held `inventory_hostname`. The value is a regular expression, so a banner containing `.` or `+` would need escaping there.

## Worked example

Start from the converged node2 serving `VersionAddendum Rocky1`, with no backups, and set `ssh_banner: Rocky"` in `group_vars/rhel.yaml`. Render computes new content that differs from the existing file, so the module copies the old file to `10_banner.conf.548.2026-10-04@15:49:26~`. It then runs `sshd -t -f` on the temporary file, which exits 255 with `invalid quotes`, and the task fails without touching the destination. Rescue begins. Remove and Revert are both guarded by `ssh_banner_result is changed`, which is false, so both are skipped. `Explain SSH Banner Failure` fails the host with the stderr text. `always:` still runs. Find, now with `become`, reads the `0700` directory and returns one file and an empty `skipped_paths`, so the guard passes. Delete loops once and reports `changed` for `.548.`. The host then leaves the play, so the second find, the final assert, the flush and the banner check never print for it. The recap reads `ok=5 changed=1 failed=1 skipped=2 rescued=1`, and the directory again holds only `10_banner.conf` (still `Rocky1`) and `50-redhat.conf`, exactly as before the run.
