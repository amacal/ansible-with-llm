## Steps

1. **Full prerequisite chain.** List every concept the topic depends on, as deep as the chain goes (a dependency's own dependencies count too).

2. **Check coverage of each prerequisite.** Derive `<slug>` from the exact title via `.index/schema.yml`'s `slug_algorithm` and `Read .index/sessions/<slug>/meta.yml` first — confirms coverage fast, gives the exact file/target/date, plus `prerequisites.yml`/`derived_from.yml`/`uses_concepts.yml` for the genuine dependency shape (if the slug guess is wrong, `grep -l 'title: "<title>"' .index/sessions/*/meta.yml` finds the right directory). Then `Read` that prerequisite's notes file for the specific module/mechanism fact the new session should reuse rather than re-derive (per "Notes writing style"), and for any caveat that file leaves explicitly unresolved ("not investigated", "untested", "only observed once") about a pattern the new exercise will reuse — an open caveat carried forward silently can surface mid-session as an unplanned failure. `grep -l '"<title>"' .history/*/*.yml` to find its history entry, `Read` that one file for session-event context (a known bug already hit, a wrong prediction already corrected, work already deferred) — `.history/` carries no module/mechanism content and no dependency field. Don't grep every history file's full content when you only need the one entry.

3. **Flag genuinely new material.** What within the topic isn't covered by any existing prerequisite — this needs full Socratic derivation from first principles, anchored with a concrete task/module/observable-effect example before any formal question (per "Pacing and assumed knowledge").

4. **Flag missing prerequisites.** `ls .index/future-targets/` (each filename's `title:` field is a topic explicitly named as future work but not yet done) — exactly this case. Cross-check `.history/` if `.index/` looks stale. Say so explicitly — may mean a review is owed first (per "Theory review"), or the topic isn't actually ready yet.

5. **Decide the target environment and exercise directory.** `docker-local` is the default — confirm whether debian-family, rhel-family, or both (a cross-target comparison exercise) fits the topic. `vagrant-local` instead, whenever the topic genuinely needs real-VM mechanism a container can't honestly provide — reboot and `wait_for_connection`, a real init/boot sequence, genuine kernel modules, real block devices (see CLAUDE.md's "Cross-target comparison") — name specifically which container limitation makes this the right call; KVM passthrough is already set up on this host, no further setup to flag. `lxd-local` instead, whenever the topic is genuinely about the connection-plugin abstraction itself (a native API connection versus SSH) rather than about the node's own realism — name that specifically, don't pick it just for a lighter-weight real-init host when `vagrant-local` would do, and flag that it depends on host-side Incus and a remote connection token (per `targets/lxd-local/README.md`) in case that hasn't happened yet. `hetzner-cloud`/`aws-cloud` whenever the topic genuinely needs real cloud infrastructure (a cloud-specific dynamic inventory plugin, IAM-aware automation, genuine network/DNS behavior) — say exactly which credential is needed; the calling conversation asks the user for it rather than silently deferring the topic. Note if the topic re-covers a pattern already implemented against a different target (e.g. this exercise's `package`/`service` logic already exists for docker-local/debian) — if so, say that part should be a quick review/citation, not fresh derivation, and that the exact Concept Title needs the target-disambiguation suffix per `.index/schema.yml`'s `cross_target_disambiguation`.

6. **Suggest a short directory name** for the exercise (`{target-dir}/{dir}/`, a short human-friendly name, not the full slug) following the grouping convention (shared prefix with related existing exercises under that target). The main conversation creates the empty directory; the user writes every file in it (fresh, or carried over from their own earlier exercises per CLAUDE.md's "Exercise files"). Containers are named `{dir}-node1`, `{dir}-node2`, ...

7. **Report back** a structured plan: (a) prerequisites to cite-and-confirm briefly, each with source notes file and the specific fact to reuse, plus any unresolved caveat that file records about a reused pattern, so the calling conversation can decide whether to raise it deliberately or leave it as a prediction test; (b) any prerequisite needing a deeper review first, and why; (c) what's genuinely new, plus a suggested concrete task/module anchor for opening it; (d) the decided target environment and why; (e) a suggested exercise directory name; (f) the current defaults from `.index/teaching/calibration.yml`, plus any dimension with thin evidence that this topic would suit trying the other variant on. No Socratic question script — the calling conversation designs the actual dialogue from this plan.
